- **Дата:** 2026-06-04
- **Статус:** approved (подход B), готов к написанию плана

- **Связано:** ClaudeMetrics backlog `t-0004` (resumable checkpoints — поглощается этим дизайном), `t-0003` (архивация/Neon storage), `t-0009` (smart-алерт деградации)

## 1. Проблема и доказательства

**Цель владельца (дословно):** «стабильный парсер колёс всех объявлений без блокировок, без превышения лимитов, без пропусков. Важно для скорости продажи: если объявление ушло в архив и пропало — потенциально продано. Пусть даже 1 раз в день, но актуализировать ВСЁ и безопасно.»

**Замеры на проде (2026-06-04):**

| Сигнал | Факт |
|---|---|
| Запуски `kolesa_full` | 25 подряд за 2 недели — все `cancelled` ровно на 350-мин таймауте (`The job has exceeded the maximum execution time of 5h50m0s`) |
| `deactivate-old` / `trigger-alive-check` | под `if: success()` → **пропущены каждый раз** |
| kolesa «активных» в БД | **157 407** |
| подтверждены живыми за 24ч | 10 403 (**6.6%**) |
| не виделись >7 дней | **130 819 (83%)** |
| не виделись >30 дней | 70 398 (45%); минимальный `last_seen_at` активного — 2026-04-21 |
| `closed_at` проставлено за последние 30 дней | **0** |
| Проба 40 «активных, но >7д протухших» URL вживую | 85% → `200` (живы, парсер не дошёл), 15% → `404` (мертвы = проданы, висят активными); **0 анти-бот челленджей** |

**Корневая причина (структурная, не параметрическая):**
1. Текущая модель брутфорсит — каждый цикл заново проходит ~12 000 страниц фидов вглубь (15 городов × до 250 стр + 81 бренд + 97 моделей + комбинаторика). Не влезает в 350-мин потолок GHA-джобы.
2. Нет резюмируемости → рестарт с фида №0 каждый раз → **хвост фидов не читается никогда** (систематическая слепая зона = «пропуски»).
3. Сигнал «продано» выводится из отсутствия в фиде + `deactivate` через 168ч. Но `deactivate` под `success()`, а `success` не наступает → **сигнал мёртв уже >30 дней** (0 закрытий).
4. `alive_check` бьёт по URL напрямую (это правильный механизм!), но смотрит только на `is_active=FALSE` (реанимация), а при `404` **не ставит `closed_at`/`is_active=FALSE`** — просто бампает `last_seen_at`. То есть детектор «продано» отсутствует как класс.

**Ключевой инсайт:** детект «продано» НЕ требует переparsинга фидов вглубь. Он требует прямого GET по URL объявления: `200` = жив, `404/410` = продан. Провалидировано вживую (id 221153415 → 200/живой, id 217539026 → 404/мёртвый). Одиночные GET'ы безопасны по rate (0 челленджей на 40 запросов с датацентр-IP при ~2 req/s).

## 2. Goals / Non-Goals

**Goals**
- Каждый цикл (цель — раз в сутки) актуализировать состояние ВСЕХ активных kolesa-объявлений: подтвердить живость или поставить `closed_at`.
- Точный детект «продано»: `closed_at` в пределах ~1 цикла после исчезновения.
- Без блокировок (анти-бот), без превышения лимитов GHA, без систематических пропусков.
- Только бесплатный облачный GHA. Полностью резюмируемо (ни один проход не обязан закончиться за одну джобу).
- Discovery новых объявлений и обновление цен сохранены.

**Non-Goals**
- Реалтайм / суб-часовая свежесть. Раз в сутки достаточно.
- Парсинг всех детальных атрибутов (mileage/engine/runs) — отдельная задача (backlog `t-0013`).
- Уход с GHA на self-hosted/платный воркер (явно отвергнуто владельцем).
- Другие источники (mycar/olx/...). Только kolesa.

## 3. Ограничения (binding constraints)

- **GHA free cloud:** per-job hard cap 6ч; берём **soft-budget 300 мин** на джобу с аккуратным выходом. Один workflow-run может содержать много джоб подряд (matrix + `max-parallel`) → суммарная работа 8–12ч укладывается в один run без нарушения per-job лимита.
- **Датацентр-IP:** анти-бот чувствителен к burst search-пагинации; одиночные listing-GET'ы провалидированы безопасными при 2–3 req/s.
- **Neon free tier ~512MB**, `statement_cache_size=0` обязателен (PgBouncer transaction pooling).
- **kolesa pagination cap:** 250 стр × 20 = 5000 объявлений на фид (никуда не делся; именно поэтому liveness идёт по известному набору, а не по фидам).
- **Public repo:** GHA-минуты безлимитны; секреты только в GitHub Secrets.
- Колонка `listings.source_id` (FK), не текст `source`. Фильтр kolesa — по `source_id`.

## 4. Архитектура (обзор)

Три резюмируемых, time-boxed, курсор-driven прохода + трекер цикла:

```
                         ┌─────────────────────────────────────────────┐
   kolesa.kz             │              Neon Postgres                   │
      ▲  ▲               │  listings(.., is_active, last_seen_at,       │
      │  │               │           last_checked_at*, closed_at)       │
      │  │               │  parse_cursor* (discovery feed progress)     │
      │  │               └───────▲───────────────▲──────────────────────┘
      │  │ GET /a/show/{id}      │ upsert+price  │ cursor R/W
      │  └───────────────┐       │               │
  GET │              ┌───┴───────┴───┐     ┌──────┴────────────┐
 list │              │ 2. DISCOVERY  │     │ 1. LIVENESS SWEEP │  (ядро)
 page │              │  (фиды,       │     │  обход ВСЕХ active │
      │              │  newest-first,│     │  по курсору        │
      └──────────────┤  early-stop)  │     │  last_checked_at   │
                     │  → новые +    │     │  200→alive         │
                     │    цены       │     │  404→closed_at=now │
                     └───────────────┘     └─────────┬──────────┘
                                                     │
                                          ┌──────────┴──────────┐
                                          │ 3. CYCLE TRACKER +  │
                                          │  safety-deactivate  │
                                          │  + Telegram summary │
                                          └─────────────────────┘
   * = новые элементы схемы
```

Liveness владеет «жив/продан» по известному набору (гарантия отсутствия пропусков). Discovery owns «новое + цена», дёшево и поверхностно. Старый deep-parse 3 шарда выводится из эксплуатации.

## 5. Компоненты

### 5.1 Схема БД (миграция в `database/migrations/`, обновить `init.sql` + README §Схема)
- `listings.last_checked_at TIMESTAMPTZ NULL` — курсор liveness (когда объявление в последний раз пинговали по URL; отличается от `last_seen_at` = когда последний раз видели живым).
- Индекс: `CREATE INDEX idx_listings_liveness ON listings (source_id, last_checked_at NULLS FIRST) WHERE is_active;` — выбирать «дольше всех не проверяли» дёшево.
- `parse_cursor(source_id, feed_key TEXT, last_page INT, cycle_id INT, updated_at)` — прогресс discovery по фидам (резюмируемость). PK (source_id, feed_key).
- Опционально `parse_cycle(id, kind, started_at, finished_at, stats JSONB)` — границы и метрики цикла (для трекера/алертов). Можно начать без отдельной таблицы и считать цикл по `min(last_checked_at)`.

### 5.2 Liveness sweep — `parsers/kolesa/liveness.py` (ядро, поглощает `alive_check.py`)
- **Выборка батча:** `SELECT id, listing_url FROM listings WHERE source_id=$kolesa AND is_active=TRUE AND listing_url IS NOT NULL ORDER BY last_checked_at NULLS FIRST LIMIT $batch` — оба «никогда не проверенные» и «дольше всех не проверенные» идут первыми. Гарантия: за достаточно волн каждое активное объявление будет проверено.
- **Проверка URL:** `curl_cffi` Chrome impersonation (как сейчас), поддержка `kolesa.kz` и `m.kolesa.kz`, `allow_redirects=True`, timeout.
- **Классификация:**
  - `200` **и** тело похоже на листинг (есть price/JSON-скелет — guard против soft-404) → `is_active=TRUE, last_seen_at=now(), last_checked_at=now()`; при включённом флаге — извлечь цену и записать в `price_history` если изменилась.
  - `404 / 410` → `is_active=FALSE, closed_at=now(), last_checked_at=now()` — **событие «продано» с таймингом**.
  - редирект на закрытую/архивную/главную страницу или soft-404 (200 без листинг-маркеров) → трактуем как closed (тот же путь, что 404), но логируем отдельно.
  - `5xx / network / timeout / -1` → **НИЧЕГО не закрываем** (`is_active`/`closed_at` не трогаем). Ставим `last_checked_at=now()` (чтобы зависший URL не блокировал голову очереди) + инкремент счётчика ошибок для наблюдаемости. Объявление перепроверится в следующем цикле наравне со всеми. Никаких закрытий на неоднозначности.
- **Rate:** concurrency 2–3, рандом delay → ~2–3 req/s. Всё через env (`LIVENESS_CONCURRENCY`, `LIVENESS_DELAY_MIN/MAX`, `LIVENESS_BATCH`, `LIVENESS_TIME_BUDGET_MIN`).
- **Анти-бот backoff:** на первый `403/429/IPBlockedError` — пауза + снижение rate; при устойчивом блоке — аккуратный выход (курсор сохранён через per-row `last_checked_at`). Никогда не закрывать объявления при подозрении на бан.
- **Time-box:** идём пока есть «протухшие» в батче и не вышли за `LIVENESS_TIME_BUDGET_MIN` (~300). SIGTERM-safe. Идемпотентно: повторный запуск просто продолжает с курсора.
- **Опция price-refresh** (по умолчанию ON — страница и так скачана): сравнить цену с последней в `price_history`, записать при изменении.

### 5.3 Discovery sweep — эволюция `parsers/kolesa/parser.py`
- **Sort newest-first:** добавить параметр сортировки kolesa «по дате, свежие первыми» в URL фида (точный query-param подтвердить при реализации).
- **Early-stop:** на фид считать число НОВЫХ `external_id` на странице; остановить фид после `EARLY_STOP_PAGES` (env, напр. 3) подряд страниц с 0 новых ID за этот цикл. 250 стр → обычно единицы.
- **Резюмируемый курсор:** писать `parse_cursor.last_page` по фиду; на старте продолжать. С early-stop обычно успевает за одну джобу, но курсор страхует.
- **Назначение сужается:** только новые объявления + обновление цены на верхних страницах. «Жив/продан» discovery больше НЕ решает — это liveness.

### 5.4 Cycle tracker + safety-deactivate
- **Цикл liveness завершён**, когда все активные проверены с момента старта цикла (`min(last_checked_at over active) >= cycle_start`).
- **Telegram-summary за цикл:** checked / alive-refreshed / closed(sold) / new-discovered / errors. (Хук для backlog `t-0009`.)
- **Safety-deactivate переписать:** старый слепой 168ч-deactivate отключаем как основной механизм (его роль теперь у liveness). Оставляем только страховку: если объявление почему-то не проверено liveness'ом > `SAFETY_DAYS` (не должно случаться, если liveness успевает) — пометить/проалертить, но НЕ закрывать массово вслепую.

### 5.5 Workflows (`.github/workflows/`)
- **`kolesa_liveness.yml`** (новый): matrix-волны с низким `max-parallel`, расписание — ежедневно (можно 2× с зазором). Резюмируемо: каждая джоба берёт следующий батч по курсору. Джоба ≤300 мин.
- **`kolesa_discovery.yml`** (или вернуть в `daily_parsers.yml` лёгким джобом): newest-first + early-stop, быстрый.
- **`kolesa_full.yml`**: deep-parse выводим из эксплуатации (отключить cron; оставить `workflow_dispatch` как аварийный full-rescan на крайний случай, либо удалить).
- **`alive_check.yml`**: поглощается liveness (active-sweep). Реанимацию недавно-inactive можно оставить вторичной опцией внутри liveness или ретайрнуть.

## 6. Поток данных (lifecycle объявления)
1. **Новое** объявление → discovery вставляет (`is_active=TRUE, last_seen_at=now(), last_checked_at=NULL`).
2. Liveness (NULLS FIRST) берёт его в ближайшую волну → подтверждает `200` (бамп `last_seen/last_checked`, цена) или закрывает `404`.
3. Пока живо — каждый цикл `200` → `last_seen_at` свежий → аналитика скорости продажи корректна.
4. **Продано** → следующий liveness-пинг даёт `404` → `is_active=FALSE, closed_at=now()`. Время в архиве = `closed_at - first_seen_at`.

## 7. Bootstrap (разовый catch-up)
- Прогнать liveness по всему бэклогу 157k, чтобы: проставить `last_checked_at` всем, **закрыть фантомы** (вернуть потерянные «продажи», `closed_at`), освежить живые.
- Размазать по волнам/суткам (157k при 2–3 req/s ≈ 15–22ч → несколько джоб в одном-двух run'ах).
- **Замерить и отчитаться:** реальный dead-rate (проба дала ~15% на >7д; на >30д вероятно выше).
- **Ожидаемый эффект (коммуницировать как корректный):** «активных» резко упадёт (закроются фантомы), аналитика выправится. Это не регресс, а починка.
- Перед записью — прогнать в **dry-run** (логировать would-close без записи) на первой 1–2k выборке, сверить глазами (правило bulk-SQL из CLAUDE.md).

## 8. Обработка ошибок и крайние случаи
- **soft-404 (200, но не листинг)** → guard по листинг-маркерам в теле; трактуем как closed, логируем отдельно.
- **Редирект на главную/поиск** → не считать alive; closed-путь.
- **`m.kolesa.kz`** URL → поддержать наравне с `kolesa.kz`.
- **Анти-бот в середине прогона** → backoff/выход, курсор сохранён, никаких закрытий.
- **Падение Neon-коннекта** → существующий retry-паттерн (`released back to the pool` → свежий коннект).
- **SIGTERM на таймауте GHA** → graceful, per-row курсор уже персистентен.
- **Никогда не закрывать на неоднозначности** (5xx/сеть/-1).

## 9. Тестирование
- **Unit:** классификатор статусов (фикстуры 200-листинг / 200-soft404 / 404 / 410 / redirect), early-stop (последовательности страниц), SQL выборки курсора.
- **Integration:** liveness на маленьком батче против реальных провалидированных URL (221153415→200, 217539026→404).
- **Dry-run режим** liveness (would-close без записи) — обязателен перед bootstrap.
- `python -m py_compile` затронутых файлов; без секретов в коде.

## 10. Поэтапный rollout
- **Phase 0 — Схема:** миграция (`last_checked_at`, индекс, `parse_cursor`), `init.sql` + README.
- **Phase 1 — Liveness:** `liveness.py` + `kolesa_liveness.yml` + dry-run → затем **bootstrap** 157k (замер dead-rate, закрытие фантомов).
- **Phase 2 — Discovery:** sort newest-first + early-stop + курсор в `parser.py`; ретайр deep-parse cron.
- **Phase 3 — Tracker/cleanup:** cycle-tracker + Telegram summary, переписать safety-deactivate, обновить README/CHANGELOG, обновить ClaudeMetrics backlog (`t-0004` → done/absorbed, добавить новые задачи).

## 11. Риски и митигации
- **Анти-бот при масштабе (liveness 8–12ч непрерывно).** Память: ~80 req/min ловил накопительный бан через ~4ч — но то была search-пагинация; одиночные listing-GET'ы безопаснее (проба: 0 челленджей). Митигация: старт консервативно 2–3 req/s, мониторинг, backoff, time-box, при желании зазоры между волнами.
- **soft-404 → ложное закрытие.** Митигация: guard по маркерам тела + dry-run + «не закрывать на неоднозначности».
- **Neon storage (157k + история).** Тянет за собой `t-0003` (архивация >30d). Liveness уменьшит активный набор (закрытие фантомов) — частично помогает.
- **kolesa меняет разметку listing-страницы.** Митигация: unit-тесты классификатора + алерт деградации (`t-0009`).

## 12. Метрики успеха
- `closed_at`-событий в сутки > 0 и отражают реальный темп продаж (сейчас 0/мес).
- Доля активных с `last_checked_at < 24ч` → ~100% в установившемся режиме (сейчас 6.6%).
- 0 отмен по GHA-таймауту; liveness-цикл закрывается ежедневно.
- Нет IP-банов (мониторинг 403/429).

## 13. Открытые вопросы (тюнятся после bootstrap)
- Точная суточная каденция и размер волн — после реального замера throughput на bootstrap.
- Нужен ли периодический deep-discovery для «хвоста» за 5000-лимитом (вероятно нет: liveness держит известный набор, а новые всплывают newest-first).
- Точный kolesa query-param сортировки «свежие первыми» — подтвердить при реализации.
