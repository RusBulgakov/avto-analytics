Этот файл читается **каждым** AI-агентом (Claude Code, Cursor, Codex, …) перед работой в этом репо. Содержит канонические правила. Если в коде или других доках есть противоречие — этот файл приоритетнее.

> Устаревший `ai_agent_instructions.md` оставлен для исторической справки; ориентируйся на этот файл.

## 📝 Правило документирования (CRITICAL)

**После КАЖДОЙ значимой доработки** — до финального commit — сделай:

### 1. Обнови `CHANGELOG.md`
Добавь запись в формате:
```markdown
## YYYY-MM-DD — короткое описание (<commit-sha>)

### Added / Changed / Removed / Fixed
- что именно поменялось (фактами, с цифрами)

### Impact
- что это значит для пользователя/данных (опционально но желательно)
```
Всегда вставляй **сверху** — самое свежее наверху.

### 2. Обнови `README.md` если изменилось хоть что-то из:
- Архитектурная диаграмма (новые сервисы/workflow)
- Источники данных (число фидов, объёмы, время парсинга)
- GitHub Actions (cron, timeout, новые workflow)
- Список API endpoints
- Структура проекта (новые директории/ключевые файлы)
- Секция "Известные особенности" (новые нюансы/решения)
- Переменные окружения (новые или переименованные)
- Deploy targets (Render / Vercel / etc.)

Цель — README = single source of truth. Читатель через 3 месяца не должен обнаруживать факты **только** в commit message.

### 3. Commit message
Должен объяснять "что" и "почему" без необходимости лезть в README. Template:
```
<type>(<scope>): <что поменялось коротко>

<подробности почему это сделано, какой эффект, какие trade-off>
```
`type` ∈ `feat | fix | refactor | docs | chore | perf | test`.

### 4. Проверь что README не врёт
Перед push пробегись глазами по цифрам в README — они часто отстают.
Особенно: число фидов, cron расписание, timeout, список endpoint'ов.

- Косметические правки CSS
- Правки комментариев в коде

## 🏗️ Ключевые архитектурные факты (не забыть при правках)

- **Deployment:** всё на **Render** (backend + frontend), парсеры — на **GitHub Actions** (public repo → unlimited minutes). Neon Postgres.
- **Next.js:** `output: 'export'` → статический экспорт. Динамические компоненты (Leaflet и т.п.) **обязаны** быть через `next/dynamic({ ssr: false })`.
- **Backend:** FastAPI + asyncpg + Neon Pooler → `statement_cache_size=0` критично, без него словишь `InvalidSQLStatementNameError`.
- **Kolesa parser:** лимит пагинации = 250 страниц × 20 = **5000 объявлений на фид**. Чтобы охватить тяжёлые бренды, добавляй model-level feed'ы (`brand/model`).
- **Deactivate threshold:** сейчас 168h (7 дней), переопределяется `DEACTIVATE_THRESHOLD_HOURS` env. Менять осторожно — слишком малое значение ложно-мертвит активные объявления.
- **Alive-check:** отдельный workflow `alive_check.yml` каждые 12h — оживляет inactive, которых kolesa всё ещё показывает живыми.

## 🧰 Технические правила для кода

1. **Absolute paths** — при правке файлов ВСЕГДА используй абсолютные пути.
2. **Read перед Edit** — сначала прочитай файл, потом редактируй (иначе Edit-tool откажет).
3. **Никаких секретов в репо** — `.env`, пароли, токены только в GitHub Secrets / Render env.
4. **Frontend static export** — ни один endpoint на фронте не должен требовать SSR. Все dynamic routes через query-string (`/listing?id=...`) или ISR-совместимый механизм.
5. **Rate-limit парсеров** — любой новый парсер обязан иметь: random delay между запросами (≥1 сек), UA-ротацию (см. `parsers/common/http_client.py::USER_AGENTS`), retry на 429/5xx с экспоненциальной задержкой.
6. **CORS:** при добавлении нового frontend-домена не забудь `BACKEND_CORS_ORIGINS` в Render-env бэка.

## 🚫 Что НЕ делать

- Не коммитить `.next/`, `node_modules/`, `__pycache__/`, `.env` (гитигнор покрывает, но проверь).
- Не делать `git push --force` на `main` без явной просьбы пользователя.
- Не трогать `airflow/` — это устаревший код, оставлен как archive.
- Не менять `database/init.sql` без обновления миграций и README. Схема БД = публичный контракт между парсерами/бэком.
- Не добавлять emoji в коммиты или код без явной просьбы пользователя.

## 🔄 Процесс работы над задачей

1. **Понять запрос** — если задача большая, разбить на TODO-список (TodoWrite).
2. **Recon** — прочитать затрагиваемые файлы, поискать конвенции (Grep/Glob).
3. **Написать код** — соблюдая правила выше.
4. **Проверить:**
   - `frontend/`: `npm run build` должен проходить.
   - `parsers/`: `python -m py_compile <файл>` не должен падать.
   - `backend/`: если трогал endpoint — проверь через curl.
5. **Документировать:** CHANGELOG + README (см. выше).
6. **Commit + push** — с содержательным сообщением.
7. **Сообщить пользователю** — что сделано, какие side-effect'ы, что нужно от него (manual deploy? запуск workflow?).
